# 기획 메모 진단: 판정 품질 평가 기준

현재 진단이 어떤 문제를 잘 찾고, 어디서 잘못된 지적을 하는지 재현 가능한 방식으로 확인하기 위한 기준이다. 실행 방법은 [README.md](README.md)에 있다.

## 1. 범위

- **보는 것:** 앱이 지금 쓰는 프롬프트, 모델 호출, 후처리(`buildReport`)를 그대로 거친 판정.
- **보지 않는 것:** 흥행, 투고 성공, 실제 사용자 메모에서의 품질. 합성 메모 결과는 "이런 유형의 문제를 잡는 구조가 동작하는가"까지만 말한다.
- 앱의 판정 로직, 프롬프트, UI는 평가하면서 바꾸지 않는다. 기준 결과를 먼저 확보하고, 수정안은 따로 제안한다.

## 2. 라벨

| 라벨 | 뜻 | 앱의 예/아니오와의 관계 |
| --- | --- | --- |
| 문제 없음 | 메모가 질문의 기준을 충족한다 | 앱이 "예"면 일치 |
| 문제 있음 | 메모 안의 내용이 기준을 어긴다(모순, 양립할 수 없는 설정) | 앱이 "아니오"면 일치 |
| 정보 부족 | 판단에 필요한 내용이 메모에 없다. 작품의 결함이라고 단정할 근거는 없다 | 앱은 "아니오"로만 표현할 수 있다. 이유와 코멘트가 "메모에 없다"고 말하는지를 사람이 본다 |
| 해당 없음 | 질문이 이 메모에 적용되지 않는다 | 앱에는 표현할 방법이 없다 |

- 라벨은 앱의 예/아니오와 따로 관리한다(`eval/labels/`). 범주별로 따로 세고, **하나의 정확도 수치로 합치지 않는다.**
- 지금 있는 라벨은 모두 AI가 쓴 **사람 검토 전 임시 라벨**이다. 전문가 정답으로 취급하지 않는다.
- 이번 샘플에는 '해당 없음'인 대상 질문이 없다. 이 범주는 아직 검증되지 않았다.

## 3. 사실 확인과 주관 판단의 분리

- **사실 확인 문항:** 메모 안에서 확인할 수 있는 것(설정 충돌, 동기 문장이 있는지, 폐기안/최종안 표시, 결말이 있는지). 임시 라벨을 달고 자동으로 집계한다.
- **주관 문항:** `genre_fit.core_fun`(장르 재미), `originality.twist`(개성), `selling_point.clear`(셀링 포인트), `protagonist_appeal.root`(주인공 매력). 라벨을 달지 않는다. 근거가 판단을 뒷받침하는지와 조언이 쓸모 있는지만 사람이 본다. 이 평가로 흥행이나 투고 성공을 검증했다고 말하지 않는다.

## 4. 평가 항목

| 항목 | 질문 | 자동 집계 | 사람 검토 |
| --- | --- | --- | --- |
| 문제 탐지 | 실제로 있는 문제를 찾는가 | '문제 있음'·'정보 부족' 대상에서 최종 답이 "아니오"인지, 반드시 찾아야 할 문제의 필수 인용이 근거에 들어갔는지 | 코멘트가 그 문제를 제대로 설명하는지 |
| 오탐 | 정상 내용이나 의도적 설정을 문제라고 하는가 | '문제 없음' 대상에서 "아니오"가 나왔는지, 하면 안 되는 지적의 인용이 "아니오"의 근거나 '어긋나는 설정'에 쓰였는지(의심 건) | 의심 건이 실제 오탐인지 |
| 근거 정확성 | 인용이 원문에 있고, 판단을 실제로 뒷받침하는가 | 원본 응답의 모든 인용을 앱과 같은 `QuoteChecker`로 확인해 원문에 없는 인용을 센다. 대상 질문에서 예상 근거가 인용됐는지, 원문에는 있지만 예상 근거가 아닌 인용(예상 밖 인용)을 표시한다 | 인용이 판단과 관련 있는지. 원문에 있기만 한 무관한 인용이 통과하는지 |
| 정보 부족 처리 | 메모에 없는 내용을 지어내거나 작품의 결함으로 단정하는가 | '정보 부족' 대상의 답, 이유·코멘트에 "메모에 없다" 류의 표현이 있는지(휴리스틱), 근거 확인 실패로 "예"가 "아니오"가 된 답과 그 답이 빨강·먼저 고칠 3가지에 들어갔는지 | 표현이 결함 단정인지, 없는 내용을 지어냈는지 |
| 수정 우선순위 | 중요한 문제가 '먼저 고칠 3가지'에 들어가는가 | 빨강 항목(목록 순), 고른 3개와 목록상 위치, 목록 순서 그대로인지, 빠진 빨강, 심은 문제가 들어갔는지 | 고른 3개가 실제로 가장 중요한지 |
| 조언의 유용성 | 어느 부분을 왜 검토해야 하는지 작가가 이해할 수 있는가 | 없음 | 1~5점 |
| 반복 일관성 | 같은 입력에서 핵심 판정이 유지되는가 | `--repeat 3`에서 질문별로 답이 바뀌었는지, 대상 질문이 바뀌었는지. 쌍 비교에서는 바꾼 부분과 무관한 질문의 답이 쌍 사이에서 달라졌는지 | 바뀐 판정 중 어느 쪽이 맞는지 |

운영 지표도 함께 기록한다: 소요 시간, 단계별 실패(모델 호출/후처리), 질문 누락·중복, 앱이 뺀 인용 수.

## 5. 샘플

기획 메모 8개를 4쌍으로 만들었다. 각 쌍은 A에 정해진 치환만 적용해 B를 만들었고, 치환마다 정확히 한 번만 맞는지 확인했다.

| 쌍 | 장르 | A | B | 대상 질문 | 임시 라벨 A → B | 하면 안 되는 지적 |
| --- | --- | --- | --- | --- | --- | --- |
| p1 | 로판 | 설정이 일관됨 | 죽은 남동생의 학비를 마련하려 하는 명확한 충돌 | `consistency.no_conflict` | 문제 없음 → 문제 있음 | 가명 '엘라', 리나의 정보원 반전을 충돌로 지적 |
| p2 | 현판 | 세 핵심 선택마다 동기 문장이 있음 | 동기 문장 세 개만 지움 | `motivation.reason` | 문제 없음 → 정보 부족 | 작가가 일부러 숨긴 미소의 정체를 동기 누락·충돌로 지적 |
| p3 | 무협 | 폐기안과 최종안이 [폐기]/[최종]으로 구분됨 | 양립할 수 없는 설정을 모두 최종안처럼 적음 | `versions.separated`, `consistency.no_conflict` | 문제 없음 → 문제 있음 | (A) 폐기안을 최종 설정과의 충돌로 지적 |
| p4 | 스릴러 | 결말이 적혀 있음 | 결말 줄만 지움 | `ending.decided` | 문제 없음 → 정보 부족 | 여러 사람이 관여한 의도적 설정을 지적, (B) 없는 결말을 지어냄 |

- 모델 입력(`eval/samples/*.json`)에는 앱이 받는 장르, 메모, 참고작만 있다. 정답과 결함 설명은 `eval/labels/*.json`에만 있다.
- 라벨마다 대상 질문 ID, 예상 판단, 근거 문장, 반드시 찾아야 할 문제, 하면 안 되는 지적, 바꾼 부분 때문에 함께 달라질 수 있는 질문(`mayAlsoChange`)을 적었다. 쌍 비교는 이 질문들을 빼고 나머지 질문이 흔들리는지 본다.
- p2는 `dev/samples`의 대본 샘플 A("남은 날")를 기획 메모 형식으로 다시 썼다. 예전 대본용 11문항 정답표는 쓰지 않고, 현재 23문항 기준으로 라벨을 새로 달았다.

**한계:** AI가 쓴 합성 메모이고 결함을 뚜렷하게 심었기 때문에 실제보다 판정이 쉽다. 같은 계열 모델이 판정하므로 결과가 실제보다 좋게 나올 수 있다. 메모가 928~1,341자로 짧아서, 수천~수만 자인 실제 메모의 성능을 대표하지 않는다.

## 6. 실행 조건

- 앱과 같은 경로를 쓴다: `diagnoseDetailed`(OpenAI Responses API background 응답) → `buildReport`. 평가용으로 진단을 따로 구현하지 않는다.
- 실행마다 샘플 ID, 회차, 모델과 추론 설정, 공급자·응답 모델·응답 ID·토큰 사용량·비용, 프롬프트·스키마·판정 규칙 파일 해시와 git 커밋, 모델 원본 응답, 최종 리포트, 원문에 없는 인용, 후처리로 바뀐 판정, 소요 시간, 성공·실패와 오류를 저장한다.
- 결과는 `eval/results/<실행 시각>/`에 저장하고 리포트 DB에는 넣지 않는다. 인증 정보와 환경 변수 값은 저장하지 않고, 오류 문구 속 비밀 값은 가린다.
- 모델 호출이 실패하면 재시도하지 않고 멈춘다. 로그인·사용 한도·네트워크 문제일 가능성이 커서 원인을 보고한다. 후처리 실패(질문 누락 등)는 결과로 기록하고 다음 샘플로 넘어간다.
- 한 번에 부르는 모델 호출 수는 `--max-calls`(기본 8)를 넘지 못한다. 반복 실행(`--repeat 3`)은 이 값을 올려야 켜진다.
- **실패를 빼고 집계하지 않는다.** 표본 수, 계획 건수, 실제 실행 건수, 실패 건수를 항상 함께 적는다.

## 7. 사람 검토 절차

1. `eval:score`가 만든 `review.csv`를 스프레드시트로 연다. 우선순위 열 1(대상 질문, 하면 안 되는 지적 의심, 근거 확인 실패로 바뀐 답)부터 본다.
2. `[검토]라벨확정`: 임시 라벨이 맞는지 정하고, 틀리면 네 라벨 중 하나로 고친다. 두 사람이 따로 채운 뒤 서로 다른 칸을 이야기로 맞추는 것을 권한다.
3. `[검토]인용이 판단을 뒷받침`: 예 / 부분 / 아니오. 원문에 있는 문장이어도 판단과 무관하면 "아니오"다.
4. `[검토]조언 이해도`: 작가가 어느 부분을 왜 봐야 하는지 알 수 있으면 5, 전혀 모르겠으면 1.
5. 주관 문항은 라벨 칸을 비워 두고 근거와 조언만 평가한다.
6. 확정한 라벨은 `eval/labels/*.json`에 반영하고 `labelStatus`를 "사람 검토 완료"로 바꾼다. 그 전까지는 모든 자동 집계가 임시 라벨 기준이다.
